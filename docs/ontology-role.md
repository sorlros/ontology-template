# 이 프로젝트에서 온톨로지의 역할

작성일 2026-11-10.

**요약**: 온톨로지는 이 프로젝트에서 기술이 아니라 설계 원리로 쓰인다. NovelAIne 이식 계획에는 RDF 나 트리플 저장소가 들어가지 않는다. "사실을 글이 아닌 구조로 관리하고, 스키마로 검증한다"는 온톨로지의 개념만 가져온다.

관련 문서: [`skeleton-approach.md`](skeleton-approach.md)(개념과 비용), [`novelaine-skeleton-port-plan.md`](novelaine-skeleton-port-plan.md)(이식 계획), [`pilot-plan.md`](pilot-plan.md)(문서 온톨로지 파일럿).

---

## 1. 온톨로지 개념이 스토리 계획에서 맡는 역할

| 온톨로지 개념 | 스토리 계획에서의 대응 | 하는 일 |
|---|---|---|
| TBox (스키마) | 엔티티 종류(인물, 장소, 물건), 속성(생사, 위치, 소지자, 관계 종류), 사건 종류와 전제 조건 | 무엇이 사실이 될 수 있는지 정한다 |
| ABox (개별 사실) | 세계 상태. `(카엘, 위치, 숲)`, `(은빛 단검, 소지자, 카엘)` | 지금 무엇이 참인지 보관한다 |
| 트리플 | 상태의 한 칸(주어, 속성, 값) | 사실의 최소 단위 |
| 제약 검증 (SHACL) | 사건의 전제 조건, 주요 사건의 `needs` | 죽은 인물의 행동 같은 모순을 막는다 |
| 출처 추적 (named graph) | 장면마다 저장하는 사건 기록 | 되돌리기, 변경 영향 판정 |
| GraphRAG | 지시서. 장면의 인물에서 한 걸음 안의 사실만 뽑는다 | 지난 이야기 대신 필요한 사실만 모델에 전달한다 |
| 엔티티 해소 | 인물·물건의 별칭 | 같은 대상의 다른 표기를 묶는다 |

핵심 역할은 두 가지다.

- **일관성**: 사실의 정본을 모델의 기억에서 스키마가 있는 구조로 옮긴다.
- **비용**: 그 구조에서 장면에 필요한 부분 그래프만 꺼내 주므로 입력이 작아진다.

---

## 2. 쓰지 않는 것

| 온톨로지의 요소 | 쓰지 않는 이유 |
|---|---|
| RDF, OWL, SHACL 라이브러리, 트리플 저장소 | 상태는 JSON 한 덩어리다. 인물 수십 명 규모에서는 그래프 DB 가 주는 이점이 없다 |
| 여러 출처의 교차 확인과 신뢰도 | 문서 파일럿의 중심 기능이지만 소설에는 출처가 하나(작가)다 |
| 충돌 감지 | 소설에서 값이 바뀌는 것은 충돌이 아니라 변화다. 사건 기록으로 대체했다 |
| 추론(역관계, 계층) | 넣지 않았다 |

---

## 3. 이 저장소의 두 갈래

서로 코드를 공유하지 않는 두 가지가 한 저장소에 있다.

| | 문서 온톨로지 파일럿 | 스토리 엔진 |
|---|---|---|
| 명령 | `onto ingest`, `export`, `serve` | `onto story`, `skeleton`, `spine` |
| 코드 | `ingest.py`, `extract.py`, `resolve.py`, `store.py`, `server.py`, `viz/` | `story.py`, `skeleton.py`, `spine.py`, `planner.py` |
| 기술 | RDF, SHACL, TriG 저장 | 순수 Python, JSON |
| 푸는 문제 | 여러 문서가 말하는 사실을 대조한다 | 한 이야기의 상태를 시간에 따라 관리한다 |
| 사실의 변화 | 값이 다르면 충돌로 표시 | 사건으로 값이 바뀐다 |
| NovelAIne 계획에 포함 | 아니오 | 예 |

처음 목표였던 "어떤 도메인에도 쓰는 온톨로지 템플릿"과 NovelAIne 이식은 개념을 공유하는 별개의 작업이다. 이식 계획은 문서 파일럿에 의존하지 않는다.

## 4. 온톨로지가 실제로 더 필요해질 수 있는 지점

지금 계획에는 없다. 스키마를 제대로 갖춘 온톨로지가 값을 하는 곳이다.

| 지점 | 지금의 한계 | 온톨로지가 주는 것 |
|---|---|---|
| 장르별 스키마 | 사건 5종과 관계 종류가 코드와 한 파일에 고정돼 있다 | 무협의 사제 관계, SF 의 함선 탑승처럼 장르마다 다른 것을 스키마 파일로 교체한다. 처음 구상한 "도메인별 TBox 교체"가 그대로 쓰인다 |
| 장소의 계층 | "왕성의 회랑"이 "왕성" 안이라는 관계가 없다. 모델이 다른 이름을 쓰면 다른 장소로 본다 | 포함 관계와 계층 추론. 추론이 필요한 첫 사례가 될 가능성이 높다 |
| 설정 문서 가져오기 | 세계는 장르·분위기·주인공에서 모델이 만든다 | 유저가 쓴 세계관 문서를 문서 파일럿의 추출 경로로 세계 정의로 바꾼다. 두 갈래가 만나는 유일한 지점이다 |
| 누가 무엇을 아는지 | 상태는 객관적 사실만 담는다 | "사실"과 "인물이 믿는 사실"을 구분하는 구조. 비밀과 오해를 다룰 수 있다 |

---

## 5. 정리

지금 단계에서 정확한 표현은 "온톨로지 기반"보다 "스키마로 검증하는 세계 상태"다. 온톨로지라는 이름에 맞는 기술을 쓰게 되는 것은 장르별 스키마 교체나 장소 계층을 넣을 때부터다.
