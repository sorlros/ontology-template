## 2. 목표 구조

```
[스토리 생성 — 서버의 작업으로 실행. 앱은 진행 상태만 조회한다]
 마법사 입력 ─▶ 접수(즉시 응답) ─▶ ① 세계·조연(빠른 모델)
                                  ─▶ ② 결말 + 주요 사건(상위 모델) ─▶ 코드 검증 ─▶ 걸린 사건만 재작성
                                  ─▶ ③ 첫 구간의 장면 카드(빠른 모델) ─▶ 코드 검증
                                  ─▶ ④ 첫 장면 본문 ─▶ 준비 완료
 단계가 끝날 때마다 결과를 저장한다. 서버가 중간에 죽으면 저장된 단계 다음부터 이어 간다.

[턴]
 선택지 선택 ─▶ 코드: 사건 적용·검사 ─▶ 코드: 지시서 조립 ─▶ 본문 생성(스트리밍) ─▶ 다음 선택지(코드가 걸러서)
 직접 입력   ─▶ 해석(빠른 모델) ─▶ 이후 같음. 성립하지 않으면 이야기 안에서 실패하는 장면으로 쓴다

[구간이 끝날 때]
 주요 사건 장면을 읽는 동안 ─▶ 다음 구간의 장면 카드(빠른 모델, 백그라운드) ─▶ 코드 검증
```

용어:

- **주요 사건**: 이야기 전체의 전환점 8~12개. 결말 포함. 스토리 생성 때 한 번 만든다.
- **구간**: 두 주요 사건 사이. 장면 3~8개.
- **장면 카드**: 한 장면에서 반드시 일어나는 사건, 선택지, 열린 부분을 적은 것.
- **지시서**: 장면을 쓸 때 모델에 주는 입력. 코드가 상태와 카드에서 조립한다.

턴당 LLM 호출: 선택지 턴 1회(본문), 직접 입력 턴 2회(해석 + 본문). 지금은 3회(입력 압축, 본문, 등장인물 분석)다.

## 3. 현재 구조에서 확인한 것

### 3.1 계획에 영향을 주는 사실

| 사실 | 위치 | 영향 |
|---|---|---|
| 마법사가 보내는 값은 장르, 분위기, 서사 유형, 주인공 이름·성격·외형, 언어, 모델뿐이다 | `frontend/lib/data/services/api_service.dart:706` | 조연·장소·물건은 모델이 만들어야 한다(①) |
| 배경 프리셋과 시작 상황 입력은 정의만 있고 쓰이지 않는다 | `creation_prompts.dart`, `api_service.dart:716` | 건드리지 않는다(D6) |

| 스토리 화면 파일이 1,901줄이다 | `story_screen.dart` | 프런트 변경의 위험(10장) |

### 3.2 확인이 필요한 것

- **백엔드의 Supabase 키 종류.** `.env.example` 은 anon 키라고 적고, 운영 문서는 service_role 키를 언급한다. 새 테이블을 "클라이언트 정책 없음"으로 잠그려면 백엔드가 service_role 키를 써야 한다.
- **OpenRouter 의 빠른 모델·Pro 모델의 실제 출력 속도.** 6.4 의 대기 시간이 여기에 달려 있다.
- **Render 무료 플랜의 휴면.** 요청이 한동안 없으면 인스턴스를 재우는 것으로 알려져 있다. 생성 중에 재워지는지, 재워졌다 깨어날 때 6.3 의 이어 가기가 도는지 확인한다.

## 5. 골격의 형식과 검증

### 5.1 세계 (`story_plans.world`)

마법사 입력(장르, 분위기, 서사 유형, 주인공)으로 모델이 만든다. 주인공은 유저가 정한 값을 그대로 쓴다.

```json
{
  "premise": "한 줄 전제",
  "viewpoint": "카엘",
  "locations": ["왕성", "숲", "항구"],
  "characters": {"카엘": {"role": "protagonist", "wants": "…", "voice": "…", "at": "왕성"}},
  "items": {"은빛 단검": {"holder": "도윤"}},
  "relations": [["카엘", "세라", "ally"]]
}
```

- 군상극(`ensemble`)은 `viewpoint` 가 `null` 이다. 지시서는 시점 인물이 아니라 장면 카드의 인물 기준으로 만들어지므로 그대로 동작한다.
- 관계 값은 언어와 무관한 키: `ally`, `enemy`, `lover`, `family`, `stranger`.

### 5.2 주요 사건 (`story_plans.spine`)

```json
{
  "id": "e07", "when": 12, "title": "배신",
  "needs": [["alive", "세라"], ["together", "세라", "카엘"]],
  "events": [{"type": "relate", "a": "세라", "b": "카엘", "kind": "enemy"}],
  "because": ["e03"],
  "meaning": "카엘이 처음으로 혼자가 된다",
  "plants": [], "pays": ["세라의 망설임"],
  "intensity": 4
}
```

| 항목 | 내용 |
|---|---|
| `when` | 이야기 속 날짜(정수). 뒤로 가지 않는다 |
| `needs` | 이 사건이 일어나려면 갖춰져야 할 상태. 종류: `alive(X)`, `at(X, 장소)`, `together(X, Y)`, `has(X, 물건)`, `rel(X, Y, 종류)`, `fact(사실)` |
| `events` | 이 사건이 바꾸는 상태. 행동, 이동, 사망, 전달, 관계 변화, 그리고 **사실 성립**(`mark`) |
| `because` | 원인이 되는 앞의 사건. 첫 사건만 비울 수 있다 |
| `meaning` | 본문을 쓸 때의 무게와 분위기 |
| `intensity` | 1~5. 장면 길이를 정하는 데 쓰고, 긴장의 굴곡 검사에 쓴다 |
| `dilemma` | 주인공이 무엇과 무엇 사이에서 고르는지. 주인공이 행동하는 사건에는 반드시 적는다 |
| `cost` | 이 사건으로 되돌릴 수 없게 된 것. 강도 3 이상인 사건에는 반드시 적는다 |

**성립한 사실** (0단계에서 추가)

위치·소지·관계로 적을 수 없는 것 — 드러난 비밀, 약속, 고백, 누가 무엇을 알게 됐는지 — 을 이름 붙은 사실로 상태에 둔다.

- 뼈대는 사건을 쓰기 전에 사실의 이름 목록(`facts`, 12개 안팎)을 먼저 정한다. 주요 사건의 `mark` 와 `needs` 의 `fact` 는 이 목록의 이름과 글자까지 같아야 하고, 어긋나면 오류다.
- 주요 사건이 앞선 사건의 결과에 기대면 `fact` 조건으로 적는다. 아직 성립하지 않은 사실이 필요하면 앞 구간의 과제가 된다.
- 구간의 장면과 선택지는 목록에 없는 새 사실을 성립시킬 수 있다. 이 사실은 뼈대의 조건이 될 수는 없지만, 상태에 남아 그 인물이 나오는 뒤 장면의 지시서(최근 8개까지)와 다음 구간의 계획에 전달된다.
- 사실은 취소되지 않는다. 부정형 조건("아직 모른다")은 없다.
- 복선의 심기·회수(`plants`, `pays`)는 같은 원리지만 따로 둔다.

### 5.3 코드가 하는 검사

지금 프로토타입에 있는 것:

- 사건의 전제 조건(죽은 인물, 다른 장소, 없는 물건), 복선의 심기·회수, 겹치는 ID, 나오지 않는 인물.

새로 만드는 것:

| 검사 | 내용 |
|---|---|
| 전제 충족 | 각 주요 사건의 `needs` 를 그 시점의 상태에서 확인한다 |
| 틈 계산 | 사건 N 뒤의 상태와 사건 N+1 의 `needs` 의 차이. 구간이 해결해야 할 과제 목록이 된다 |
| 원인 | 첫 사건을 뺀 모든 사건의 `because` 가 앞의 사건을 가리킨다 |
| 시간 | `when` 이 감소하지 않는다. 간격이 큰 구간에 "시간 경과" 표시 |
| 재등장 준비 | 주요 사건에 필요한 인물이 직전 3개 사건에 나오지 않았으면 경고. 구간 계획의 과제에 넣는다 |
| 자동 전제 | 사건에 나오는 인물의 `alive` 를 `needs` 에 자동으로 더한다(모델이 빠뜨려도 잡히게) |
| 뼈대 보호 | 남은 주요 사건의 `needs` 에 필요한 인물·물건의 목록. 선택지를 거를 때 쓴다(7.3) |

짜임새 검사(0단계에서 추가, `spine.py` 의 `check_craft`). 사실의 모순이 아니라 극의 형식을 본다. 걸리면 사실의 오류와 같은 방식으로 사유를 돌려주고 다시 받는다.

| 검사 | 기준 |
|---|---|
| 결말의 대가 | 마지막 3분의 1에 죽음, 관계의 단절, 주인공이 물건을 내놓는 일 가운데 하나 |
| 주인공의 능동성 | 주인공이 직접 행동하는 사건이 절반 이상 |
| 적대자의 능동성 | 적대자가 먼저 움직이는 사건이 다섯 개마다 하나 이상 |
| 조연의 쓰임 | 조력자와 적대자가 각자 한 번 이상 직접 행동 |
| 긴장의 굴곡 | 가장 강한 사건이 마지막 3분의 1에 있고, 뒤쪽 평균이 앞쪽보다 높고, 후반부에 절정 전 한 번 꺾인다 |
| 대가·딜레마 칸 | 위 `dilemma`, `cost` 의 조건 |

형식이 갖춰졌는지만 본다. 대가가 이야기에서 무게를 갖는지는 판단하지 못한다. 기준 수치는 임의로 정한 값이다. 군상극과 역할이 없는 세계에서는 해당 검사를 건너뛴다.

### 5.4 생성 절차 (D3, D4, D5)

1. **세계와 조연** — 빠른 모델, 출력 약 500토큰.
2. **결말** — 상위 모델. 결말의 상태(누가 살아 있고 관계가 어떤지)와 한 줄 요약.
3. **결말에서 거꾸로 주요 사건 8~12개** — 2와 같은 호출에서 함께 받는다. 출력 약 2,500토큰.
4. **코드 검사** — 5.3 전체.
5. **재작성** — 걸린 사건의 ID 와 사유를 주고 그 사건들만 다시 받는다. 최대 2회. 그래도 오류가 남으면 `status = failed` 로 두고 3부터 다시 한다(전체 최대 3회).

모델 배정: 1은 `PRIMARY_FAST_LLM_MODEL`, 2~5는 `PRIMARY_PRO_LLM_MODEL`. 스토리에 설정된 모델(`llm_model`)은 본문에만 쓴다.

이 모델들은 값을 목록으로 강제하는 출력 형식을 보장하지 않는다(`chat_service.py:350` 의 JSON 복구 코드가 그 증거다). 형식·이름 검사는 전부 코드가 하고, JSON 이 깨지면 그 호출을 실패로 처리해 다시 시도한다.

## 6. 스토리 생성 흐름 (D10, D11)

### 6.1 순서

| 단계 | 내용 | 모델 | 저장되는 것 |
|---|---|---|---|
| 접수 | `stories` 행(`status = generating`)과 `story_plans` 행(`status = queued`)을 만들고 바로 응답한다 | — | 마법사 입력(`seed`) |
| ① 세계 | 조연, 장소, 물건, 관계, 한 줄 전제. 제목·설명·주인공 소개도 여기서 받는다 | 빠른 모델 | `story_plans.world`, `stories` 의 제목·설명, `characters` |
| ② 결말·주요 사건 | 5.4 의 절차. 코드 검증, 걸린 사건만 재작성(최대 2회) | 상위 모델 | `story_plans.spine` |
| ③ 첫 구간 | 첫 주요 사건과 둘째 주요 사건 사이의 장면 카드, 그리고 첫 장면이 끝난 뒤의 선택지 | 빠른 모델 | `story_beats` |
| ④ 첫 장면 | 첫 주요 사건의 본문. 지시서(7.5)로 쓴다 | 스토리의 모델 | `scenes` 1행, `stories.world_state` |
| 완료 | `story_plans.status = ready`, `stories.status = active` | — | |

- 첫 장면은 결말과 뼈대가 정해진 뒤에 쓴다. 뼈대가 첫 사건에 배정한 복선(`plants`)이 지시서에 들어가므로 결말을 향한 복선을 첫 장면부터 심을 수 있다.
- 첫 장면을 쓰는 모델에 결말 자체는 주지 않는다. 필요한 것은 그 장면의 복선뿐이고, 결말이 본문에 새어 나갈 위험을 줄인다(D5).
- 단계마다 끝나면 결과와 `step` 을 저장한다. 다음 단계는 저장된 것만 읽고 시작한다.

### 6.2 서버에서 끊기지 않게 하는 방법 (D11)

**요청과 작업을 분리한다.** 지금의 `create_story` 는 요청 안에서 생성을 끝까지 실행하므로 앱이 화면을 벗어나 연결이 끊기면 생성도 끊긴다. 이미지·BGM 생성과 같은 구조로 바꾼다.

1. `POST /api/stories` 는 행만 만들고 `BackgroundTasks` 에 작업을 걸고 바로 응답한다(스토리 ID 포함).
2. 작업은 서버 프로세스 안에서 요청과 무관하게 돈다. 앱이 화면을 벗어나거나 닫혀도 계속된다.
3. 앱은 `GET /api/stories/{id}/generation` 으로 상태만 조회한다. 조회를 멈춰도 작업에는 영향이 없다.
4. 돌아온 유저는 스토리 목록에서 "생성 중" 또는 완성된 스토리를 본다.

### 6.3 서버가 중간에 죽었을 때 이어 가기

프로세스 안의 작업은 서버 재시작·배포·휴면 때 사라진다. 그래서 작업을 **단계 단위로 다시 시작할 수 있게** 만든다.

- **임대(lease)**: 작업을 잡은 실행은 `lease_until` 을 지금부터 6분 뒤로 적고, LLM 호출을 시작할 때마다 다시 늘린다. 살아 있는 실행은 임대를 계속 갱신한다.
- **이어받기**: `status` 가 `queued` 또는 `running` 인데 `lease_until` 이 지났으면 죽은 작업이다. 이어받는 실행은 `lease_until` 이 지난 행만 갱신하는 조건부 업데이트로 작업을 잡는다. 갱신된 행이 없으면 다른 실행이 먼저 잡은 것이므로 물러난다(gunicorn worker 가 여럿이어도 두 번 실행되지 않는다).
- **이어받기가 일어나는 시점**: 서버가 시작할 때 한 번 훑고, 진행 상태 조회가 올 때와 스토리 목록 조회가 올 때 그 유저의 죽은 작업을 확인한다.
- **재개 지점**: `step` 다음 단계부터. 세계가 저장돼 있으면 세계를 다시 만들지 않는다.
- **실패 처리**: 한 단계가 정해진 횟수(5.4) 안에 통과하지 못하거나 외부 오류가 나면 `attempts` 를 올리고 그 단계를 다시 한다. 전체 3회를 넘으면 `status = failed`, `stories.status = failed` 로 두고 유저가 다시 시도할 수 있게 한다.

**보장의 범위**: 서버가 살아 있는 동안은 끊기지 않는다. 서버가 죽으면 다음에 서버가 뜨거나 누군가 조회할 때 이어 간다. 아무 요청도 없는 상태에서 스스로 깨어나 이어 가려면 별도의 작업 서버나 예약 실행이 필요한데, 지금의 무료 플랜 구성에는 없다(12장).

### 6.4 대기 시간

0단계에서 Codex 의 기본 모델로 잰 값(6회):

| 단계 | 소요 |
|---|---|
| ① 세계 | 21~33초 |
| ② 결말·주요 사건 | 100~212초(짜임새 검사와 사실을 넣은 뒤 188~212초, 재작성 1회에 16~17초) |
| ③ 첫 구간 | 43~112초(재작성이 있으면 최대 148초) |
| ④ 첫 장면 | 재지 않음. 지금의 첫 장면 생성과 같은 분량이다 |
| ①~③ 합계 | 3분 21초~6분 18초 |

NovelAIne 이 쓸 OpenRouter 모델의 값은 2단계에서 다시 잰다. 앱은 `step` 으로 "세계를 만드는 중 → 결말을 정하는 중 → 주요 사건을 엮는 중 → 첫 장면을 쓰는 중"을 보여 준다.

### 6.5 남용과 중복 방지

- 한 유저가 동시에 생성할 수 있는 스토리는 2개까지. 넘으면 429 를 돌려준다. 생성 한 번이 상위 모델 호출을 여러 번 쓴다.
- 앱은 생성 요청마다 `request_id` 를 붙인다. 같은 ID 로 다시 오면 새로 만들지 않고 기존 스토리를 돌려준다(시작 버튼을 두 번 누르는 경우).
- 생성 중인 스토리를 지우면 작업도 멈춘다. 실행 중인 단계는 끝난 뒤 저장할 때 행이 없는 것을 보고 그만둔다.

## 7. 턴 처리

### 7.1 구간의 장면 카드

구간에 들어설 때(주요 사건 장면이 생성되기 시작할 때) 다음 구간을 미리 계획한다.

- 모델에 주는 것: 한 줄 전제, 직전 주요 사건, 다음 주요 사건의 제목과 `needs`, 틈 목록(5.3), 현재 상태의 이름 목록.
- 받는 것: 장면 카드 3~8개. 카드마다 반드시 일어나는 사건, 열린 부분, 복선, **선택지 후보 4~5개**. 새 조연·장소가 필요하면 함께 선언한다.
- 직전 주요 사건의 장면이 끝난 뒤에 보여 줄 선택지 후보도 함께 받는다(주요 사건에는 선택지가 없으므로, 그 뒤를 잇는 구간이 만든다).
- 코드가 카드를 순서대로 적용해 구간 끝에서 다음 주요 사건의 `needs` 가 충족되는지 확인한다. 부족하면 부족한 항목을 알려 주고 다시 받는다(최대 2회).
- 빠른 모델, 출력 약 800토큰.

### 7.2 선택지

| 종류 | 사건 | 영향 |
|---|---|---|
| 태도(`tone`) | 없거나 `act` 뿐 | 그 장면의 본문만 달라진다 |
| 행동(`action`) | 사실 성립, 이동, 전달, 관계 변화 가운데 하나 이상 | 상태에 남는다. 뒤 장면의 지시서가 달라지고, 구간의 남은 카드가 성립하는지 다시 본다 |

- 종류는 모델이 적은 값이 아니라 **효과로 정한다**. 말을 거는 것만 있는 선택지는 "행동"이라고 적혀 있어도 태도로 본다.
- 행동 선택지의 대부분은 사실 성립이다("약속한다, 밝힌다, 숨긴다, 거절한다"). 물리적 상태를 건드리지 않고도 선택이 뒤에 남는다.
- 장면마다 내놓을 수 있는 선택지 가운데 행동과 태도가 각각 하나 이상 있어야 한다. 없으면 구간을 다시 받는다.

- 장면 카드의 선택지 후보에서, 턴마다 코드가 지금 상태에서 성립하고 뼈대를 깨지 않는 것만 남겨 3개를 고른다. 태도 선택이 적어도 하나, 행동 선택이 적어도 하나 들어가게 한다.
- 3개가 안 남으면 빠른 모델에 그 장면의 선택지만 다시 받는다.
- 다음 장면 자체를 바꾸는 방향 선택은 이 계획에 넣지 않는다(12장).

### 7.3 뼈대 보호

선택지의 사건을 가상으로 적용해, 남은 주요 사건의 `needs` 가 **구간 계획으로 회복할 수 없게** 되는지 본다.

- 회복 불가: 필요한 인물의 사망. → 그 선택지는 내놓지 않는다.
- 회복 가능: 위치, 소지품, 관계. → 허용하고, 구간의 남은 카드를 다시 계획한다.

### 7.4 턴 하나의 순서

**선택지를 골랐을 때**

1. 그 선택지의 사건을 적용한다(코드).
2. 구간의 남은 카드를 다시 적용해 본다(코드). 성립하지 않는 카드가 있으면 그 지점부터 구간을 다시 계획한다(빠른 모델 1회, 드물다).
3. 다음 카드의 사건을 적용하고 지시서를 조립한다(코드).
4. 본문을 생성해 스트리밍한다(스토리의 모델).
5. `scenes` 에 유저 행(고른 선택지의 문구)과 AI 행(본문, `beat_id`, `events`)을 저장하고 `world_state`, `current_beat_seq` 를 갱신한다.

**직접 입력했을 때**

1. 해석: 빠른 모델에 현재 지시서와 유저의 글을 주고 `{events: […], summary: "…"}` 를 받는다. 출력 약 100토큰.
2. 코드가 사건을 검사한다.
   - 성립하고 뼈대를 깨지 않음 → 선택지와 같은 경로. `summary` 는 지시서의 "독자의 뜻"에 넣는다.
   - 성립하지 않거나 뼈대를 깸 → 사건을 적용하지 않고, 지시서에 "독자가 시도한 것: …, 이 시도는 이루어지지 않는다"를 넣어 이야기 안에서 실패하는 장면을 쓰게 한다. 거부 메시지를 띄우지 않는다.
3. 이후 선택지 경로의 3~5와 같다.

### 7.5 지시서 (D7, D9)

| 조각 | 분량(추정) | 출처 |
|---|---|---|
| 공통 규칙과 형식 | 약 400토큰 | 고정 문구(지금의 시스템 프롬프트에서 서사 유형별 규칙을 가져온다) |
| 장면의 사실 | 약 300토큰 | 프로토타입 `brief` — 인물의 생사·위치, 같은 장소의 인물, 관계, 쓰는 물건, 반드시 일어날 사건, 열린 부분, 복선 |
| 등장인물의 말투와 원하는 것 | 약 300토큰 | `world` 에서 그 장면의 인물만 |
| 독자의 뜻 | 약 30토큰 | 고른 선택지의 문구 또는 직접 입력의 요약 |
| 직전 장면의 끝부분 | 약 400토큰 | `scenes` 의 마지막 AI 행 |
| 분량 지시 | 한 줄 | `intensity` 에서. 전환 장면은 짧게, 주요 사건은 길게 |

합계 약 1,400토큰. 지난 장면의 요약, 캐릭터 임베딩 검색, 입력 압축은 쓰지 않는다.

### 7.6 본문과 상태의 관계

- 본문은 상태를 바꾸지 못한다. 상태는 카드와 선택지의 사건으로만 바뀐다. 그래서 본문에서 사건을 추출하는 호출이 없다.
- 모델이 지시서에 없는 일을 본문에 쓰는 것(지시서 밖의 인물을 죽이는 등)은 막지 못한다. 공통 규칙에 "지시서의 사건 외에 생사·위치·소지품·관계를 바꾸는 일을 쓰지 않는다"를 넣고, 12장의 측정 항목으로 둔다.

| 뼈대 초안의 오류·짜임새 문제 | 4차: 2편에서 각 1건 | 0건. 사실의 이름이 어긋난 경우 없음 |
| 상태를 바꾸는 선택지 | 구간 재생성 6편: 60개 중 0개 / 4차: 40개 중 6개 | 44개 중 22개(전부 사실 성립) |

- 주요 사건들이 사실로 이어졌다. 예: "명부가 밤마다 이름을 지운다" → "도겸이 감춘 실종 기록이 명부에 있다" → "소거된 이름이 제방을 붙든다". 코드가 이 연결을 검사한다.
- 선택지가 서로 갈리는 결과를 남긴다. 예: "기석에게 기억의 공백을 밝힌다" / "숨긴다" 는 서로 다른 사실을 남기고, 기석이 나오는 뒤 장면의 지시서가 달라진다.
- 판타지의 구간 첫 시도는 선택지가 전부 성립하지 않아 다시 받았다(96초).

읽어 보고 확인한 한계:

- **사실이 흔해진다.** 구간의 장면이 "하린이 태오에게 항해일지를 살펴보겠다고 밝혔다" 같은 사소한 일까지 사실로 남긴다. 지시서에는 최근 8개만 넣지만, 무엇이 중요한지는 가리지 못한다.
- **선택지가 남긴 사실을 뼈대가 쓰지 못한다.** 뼈대는 먼저 만들어지므로 선택에서 나온 사실을 조건으로 삼을 수 없다. 선택의 흔적은 본문의 재료로만 쓰인다.
- **결말의 대가 검사를 글자만 맞춘 사례가 또 나왔다.** 로맨스는 주인공이 물건을 내놓는 사건으로 검사를 통과했고 결말은 "함께 미래를 선택한다"였다.
- **선택지 걸러내기는 여전히 한 번도 걸러내지 않았다**(누적 260개). 안전망으로만 남는다.
- 대기가 더 길어졌다. 뼈대 생성이 처음(100~169초)보다 1분 가까이 늘었다.

**넣기 전의 기록**

1. **선택지가 상태를 거의 바꾸지 않았다.** → 성립한 사실로 해결(위 표). 구간만 다시 만든 6편의 "행동" 선택지 60개 가운데 상태(위치, 소지품, 관계, 생사)를 바꾸는 것이 0개였다. 3차에서는 판타지 1편에서만 12개 중 6개가 상태를 바꿨고 나머지 2편은 0개다. 선택지 걸러내기와 뼈대 보호(7.2, 7.3)는 176개 후보에서 한 번도 걸러내지 않았다. 뼈대를 깨지 않는 의미 있는 행동은 대부분 "말한다, 약속한다, 숨긴다, 알아낸다"인데 지금의 상태에는 이것을 담을 칸이 없다.
2. **줄거리의 핵심이 상태 밖에 있다.** 생성된 이야기들은 비밀의 폭로, 증언, 약속으로 움직인다. 코드의 검사는 이동·소지·생사만 본다. 초안 오류가 9편 모두 0건인 것은 코드가 보는 범위가 모델에게 쉬운 부분이기 때문일 수 있다.
3. 제안했던 "성립한 사실"은 채택해 구현했다(5.2, 7.2).

### 1단계 — 백엔드 기반

- 4장의 마이그레이션, `story_state.py`, `story_skeleton.py`, 시험(unittest. CI 가 `unittest discover backend/tests` 를 돌린다).
- 검증: `PYTHONPATH=backend python -m unittest discover backend/tests -v`, 기존 시험 전부 통과.

### 2단계 — 스토리 생성

- `story_planner.py`, 생성 작업(`story_generation.py`: 단계 실행, 임대, 이어받기), `create_story` 변경, `GET …/generation`, `retry`.
- 환경 변수 `SKELETON_MODE_ENABLED`(기본 꺼짐)로 감싼다. 꺼져 있으면 지금과 똑같이 동작한다.
- 검증: 가짜 모델로 정상·재작성·3회 실패 경로의 시험. 이어 가기 시험 — 단계마다 중간에 끊고 다시 실행해 끝난 단계를 반복하지 않는지, 두 실행이 동시에 잡으려 할 때 하나만 도는지, 같은 `request_id` 로 스토리가 하나만 생기는지.
- 스테이징: 켜고 스토리 5개를 만들어 ①~④의 소요 시간과 실패 횟수를 기록. 생성 요청 직후 앱을 닫고 몇 분 뒤 열어 완성돼 있는지, 생성 중에 서버를 재시작한 뒤 조회하면 이어 가는지 확인.

### 3단계 — 턴 처리(선택지만)

- `story_play.py`, `POST …/play`(choice_id), `GET …/play`, `undo`.
- 검증: 가짜 모델로 — 선택지 적용, 구간 재계획, 뼈대 보호로 선택지가 빠짐, 중복 요청, 되돌린 뒤의 상태가 처음부터 적용한 것과 같음. 스테이징에서 API 만으로 한 구간을 끝까지 진행.

### 4단계 — 프런트

- 9장. 검증: `flutter analyze`, `flutter test`, 스테이징에서 새 스토리 생성 → 진행 화면을 벗어났다가 목록에서 다시 들어가기 → 20턴 진행 → 되돌리기, 기존 스토리가 그대로 이어지는지.

### 5단계 — 직접 입력

- 해석 호출, 성립하지 않는 입력의 이야기 안 실패 처리, 프런트의 직접 입력 연결.
- 검증: 가짜 모델로 성립·불성립·뼈대 훼손 세 경로. 스테이징에서 죽은 인물을 되살리는 입력, 다른 장소의 인물과 대화하는 입력을 넣어 본다.

### 6단계 — 전환

- `SKELETON_MODE_ENABLED` 를 기본 켜짐으로 바꾼다. 이 시점부터 D1 이 적용된다.
- 12장의 측정을 운영 데이터로 시작한다.

## 12. 범위 밖 / 나중

| 항목 | 미룬 이유 |
|---|---|
| 방향 선택(다음 장면 자체가 갈라짐) | 골격이 한 줄에서 갈래 구조가 된다. 선택지 방식이 자리 잡은 뒤에 |
| 뼈대의 뒷부분 다시 짜기(필요한 인물의 사망 허용) | 상위 모델 호출과 긴 대기가 필요하다. 지금은 그런 선택지를 내놓지 않는 것으로 막는다 |
| 본문 캐시와 독자 간 공유 | "남의 골격으로 플레이" 기능이 생겨야 의미가 있다 |
| 생성 완료 알림(푸시) | 앱에 알림 기능이 있는지 확인하지 않았다. 지금은 목록에 들어와야 완성을 안다 |
| 요청 없이도 스스로 이어 가는 작업 서버 | 별도의 작업 서버나 예약 실행이 필요하다. 무료 플랜 구성에 없다 |
| 기존 스토리를 골격 기반으로 전환 | 지난 장면에서 상태를 추출하고 뼈대를 새로 짜야 한다 |
| 누가 무엇을 아는지, 약속, 감정의 정도 | 상태가 다루지 않는다 |

운영에서 측정할 것:

1. 본문이 지시서 밖의 상태 변화를 쓰는 빈도 — 장면을 표본으로 뽑아 사람이 읽는다.
2. 구간 재계획이 일어나는 턴의 비율과 그때의 추가 지연.
3. 선택지가 3개 미만으로 남아 다시 받는 빈도.
4. 직접 입력의 사용 비율, 그중 성립하지 않아 실패 장면으로 처리된 비율.
5. 턴당 실제 입력·출력 토큰.

## 13. 위험과 결정이 필요한 것

**위험**

| 위험 | 대응 |
|---|---|
| 모델이 `needs`·`because` 를 부실하게 채워 검증이 형식만 통과한다 | 0단계에서 실제로 재고, 사람이 읽어 확인한다 |
| 뼈대 생성이 3회 모두 실패한다 | 빠른 모델로 주요 사건 5개짜리 짧은 뼈대를 만들어 진행하고, 실패를 기록한다 |
| 몇 분의 대기 중에 유저가 떠나 돌아오지 않는다 | 생성은 끝까지 진행되고 목록에 남는다(D11). 떠난 유저의 생성 비용은 그대로 든다 → 동시 생성 2개 제한(6.5) |
| 서버가 재시작·휴면으로 작업을 잃는다 | 단계별 저장과 임대로 이어 간다(6.3). 아무 요청도 없으면 다음 요청 때까지 멈춰 있다 |
| 다음 구간의 계획이 주요 사건 장면을 읽는 시간보다 오래 걸린다(0단계 실측 43~112초) | 구간 계획을 한 구간 앞서 시작한다. 그래도 늦으면 선택지 대신 대기 표시를 보여 준다 |
| 생성 대기가 실측보다 길어진다 | 2단계에서 실제 모델로 재고, 길면 주요 사건 수를 줄이거나 뼈대 모델을 바꾼다 |
| 선택이 뒤에서 합쳐져 "무엇을 골라도 같다"는 인상 | 행동 선택을 매 턴 하나 이상 넣고, 그 결과가 다음 장면의 지시서에 반영되는지 시험한다 |
| 백엔드가 anon 키를 쓰고 있어 서버 전용 테이블을 못 읽는다 | 1단계 전에 확인(3.2) |
| 스토리 화면 수정의 회귀 | 선택지 영역을 별도 위젯으로 두고, 기존 스토리의 이어 쓰기를 4단계 검증에 넣는다 |

**결정이 필요한 것**

| 항목 | 기본안 | 다른 선택 |
|---|---|---|
| 기존 스토리의 기존 경로를 언제 없앨지 | 정하지 않고 남겨 둔다 | 기한을 두고 읽기 전용으로 바꾼다 / 전환 도구를 만든다 |
| 뼈대 생성 모델 | Pro 모델(품질 우선). 대기는 2단계에서 잰다 | 빠른 모델(대기가 짧고 인과가 약할 수 있음) |
| 주요 사건의 수 | 10개 안팎(0단계에서 8~12개로 지시해 10~11개가 나왔다) | 장르나 유저 설정에 따라 조절 |
| 직접 입력의 횟수 제한 | 두지 않는다 | 무료 횟수를 둔다(직접 입력이 가장 비싼 경로다) |
| 완결 뒤의 동작 | 완결 표시 후 읽기만 | 후일담 구간을 새로 계획해 이어 쓴다 |
